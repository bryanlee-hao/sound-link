# Sound Link 局域网与 BLE 双通道通信设计

状态：设计草案，未实现。日期：2026 年 10 月 15 日。基线：当前工作区的 0.4.10 实现。

本方案让已配对的 Mac 与 Android 同时具备局域网和 BLE 通信能力。日常协调优先使用持续的 BLE 连接，局域网提供兼容与回退；两条通道共用一个协调会话和动作去重入口。目标是用户带着两台设备从公司到家、使用不同 Wi-Fi 或手机移动数据时，只要设备在蓝牙范围内，核心协调仍可运行。

现有设备身份、配对、目标耳机映射和用户授权继续保留。升级不要求重新扫码，也不要求先连通局域网才能启用 BLE。锁屏稳定性以真实息屏测试作为发布门槛，不能仅凭 GATT 已连接或收到了广播判定通过。本轮仅形成设计，不改变现有软件行为。

## 设计决策与范围

| 项目 | 拟采用的方案 |
|---|---|
| 实时状态与耳机协调 | BLE GATT 持续连接，状态变化立即发送，Mac 可主动通知手机 |
| 局域网兼容 | 保留既有 HTTPS v1；新版增加承载统一消息的 HTTPS v2 请求响应接口 |
| 通道选择 | BLE 优先；BLE 无响应时使用已验证的 LAN；两条通道可同时存在，但不各自创建事务 |
| 安全与身份 | 复用长期身份，BLE 新建经过双向认证和加密的短期会话 |
| 自动恢复 | 统一恢复调度器，使用在场、广播、网络与生命周期事件；有限主动重试 |
| 锁屏运行 | 伴生服务与 connectedDevice 前台服务支持持续监听；事件驱动，不依靠三秒定时器唤醒 |
| 现有耳机控制 | 保留五秒事务期限、目标版本校验、本地授权、恢复基线和失联失败锁 |
| 大数据 | APK、更新和完整诊断导出继续走现有下载或局域网路径，不塞进 BLE 控制队列 |

本阶段不增加公网中继，不承诺远距离通信，不转发音频，不改成蓝牙 PAN 网络，也不实现新的纯 BLE 首次配对流程。新用户仍可按现有方式下载安装并完成首次绑定；已配对用户升级后可以在没有共同局域网的情况下恢复通信。

用户无需到系统蓝牙设置里手动把 Mac 与手机配成音频设备。应用负责建立 GATT 连接；蓝牙权限和必要的伴生授权仍由用户确认。Mac 与手机的产品绑定、Android 伴生关联、AirPods 自身的配对及控制授权是不同记录，不能互相替代。系统伴生关联本身不会建立数据连接。[Android 伴生设备](https://developer.android.com/develop/connectivity/bluetooth/companion-device-pairing)

### 锁屏证据说明了什么

已有息屏记录中，同一手机进程的任务执行间隔出现约 46–61 秒，其中大部分是设备深睡；线程获得运行机会后，心跳又能很快成功。另一次 Mac 起播后，等待手机下次轮询约 8.46 秒才发送状态，超过五秒交接期限。这说明当前定时轮询不足以承担锁屏实时下行，不能把全部延迟归因于 IP 变化或进程被杀。[现有实机记录](validation.md#2026-10-15-1213-前后息屏诊断)

已有真实 GATT 读取与 TLS 恢复记录，但尚无持续 GATT 通知在深睡下可靠送达的验收结果。新方案的关键假设是：保持订阅后，BLE 数据事件能比等待应用定时轮询更及时地进入手机回调。该假设必须单独验证。

### 需要在实现阶段解决的耦合

- 当前 GATT 读完地址就关闭，没有持续消息订阅；`endpoint.available` 还与局域网地址存在绑定。新版必须允许“无局域网地址但 BLE 协调可用”。
- 当前 HTTPS 心跳和候选地址验证共用串行 worker。网络请求阻塞时不能连带堵住 BLE 事件和五秒事务。
- 当前约三秒心跳、十秒状态有效期、连续失败超过 75 秒后暂停网络重试，不能直接作为双通道整体生命周期。
- 当前手机 `handoff_consumed` 只保存最后一个 `id:action`。双通道乱序可能形成 A、B、A，单项去重不足。
- 当前认证 epoch 属于 HTTPS 会话。BLE 认证和 LAN token 更新不能各自替换业务 epoch，导致正常事务互相取消。
- 当前本地独立接管已经有 `localControlGeneration` 和失败恢复标识。通道恢复不能清除这些约束，也不能自动解锁失败状态。

## 总体结构与通道选择

```text
播放与耳机观察                   播放与耳机观察
      │                               │
Mac 协调状态机                  Android 执行与本地策略
      │                               │
逻辑会话与消息路由  ═══════════  逻辑会话与消息路由
      ├── BLE 认证加密消息 ────────────┤
      └── LAN 固定身份 HTTPS ─────────┘
      │                               │
平台音频与蓝牙接口                平台音频与蓝牙接口
      └────────── AirPods ────────────┘
```

每端仅有一个串行的业务入口。LAN、BLE 各自完成 I/O、限流和校验，再把消息交给这个入口。平台连接耳机的动作只能由业务入口授权；某条通道连上、断开或恢复，本身都不是切换耳机的理由。

| 可用条件 | 实时协调路径 | 行为 |
|---|---|---|
| BLE 与 LAN 都可用 | BLE 优先，LAN 备用 | 正常命令只选一条发送；超时后以同一事务 ID 回退 |
| 仅 BLE 可用 | BLE | 核心状态、目标确认、协调与结果均可通信，不等待 Wi-Fi |
| 仅 LAN 可用 | HTTPS v2，旧端为 v1 | 保留现有事件立即上报与约三秒轮询；息屏下行可能延迟 |
| 两条都不可用 | 不发送远端动作 | 保留既有本地失联策略和失败锁，界面说明当前为本地行为 |
| 用户暂停或撤销配对 | 均停止协调 | 不用另一条通道绕过用户意图 |

BLE 稳定工作时，停止普通三秒 LAN 轮询。LAN 在网络改变、显式刷新、更新下载或 BLE 异常时按需验证，不维持双倍高频心跳。因此“LAN 备用”可能是已验证热备，也可能需要重新认证的冷备，界面和性能指标必须区分。

LAN 只有在同一网络路径和逻辑会话中、十秒内完成应用层往返且权限仍有效时才算热备；其他情况都按冷备处理。BLE 故障后手机应立即发起 LAN 交换，但 Mac 无法通过现有 HTTPS 主动叫醒手机，不能把“Mac 有备用地址”算作可立即送达的下行热备。

通道故障立即允许回退；恢复到 BLE 优先要求连续三次应用层往返成功、稳定至少十秒，且当前无硬件事务。切换偏好不清空事件水位、不延长事务期限。五秒事务内只允许一次跨通道回退；剩余预算不足时结束本轮，不重新生成一笔等价事务。

第一阶段不新增 WebSocket。HTTPS v2 与 BLE 复用统一业务消息，但 LAN 下行仍由手机请求承载。将来即使增加 WSS，也不能据此宣称解决 Doze 调度问题。

## 会话与消息一致性

### 三层状态

| 层次 | 关键状态 | 判断依据 |
|---|---|---|
| 用户意图 | 已绑定、自动恢复开启、主动暂停 | 持久记录；进程重建不改变 |
| 单条通道 | 不可用、连接中、认证中、已验证、待确认 | 通道回调与应用层往返，不依靠广播判断在线 |
| 逻辑协调 | 同步中、可协调、需刷新状态、失联、已停止 | 身份、协调代次、目标、双方状态与授权共同决定 |

GATT 显示 connected 只证明底层连接状态。认证成功证明对端身份；应用层确认说明最近能往返；执行前的新鲜样本与授权才允许控制。这三种证据分别记录和展示。

### 一个逻辑会话承载多条通道

Mac 为已绑定手机建立随机 `coordinationEpoch`，绑定双方进程实例、用户控制代次与配对记录。第一条完成认证和同步的通道建立该会话；第二条通过同一身份认证后显式加入，不另开一套协调状态机。所有加入和替换操作在 Mac 串行执行。

每条通道另有 `transportSessionId` 与加密或 TLS 会话状态。更换 IP、重建 GATT 或更新 LAN token 不必改变仍有效的逻辑会话。双方进程实例改变、明确暂停、目标切换、解除配对或两条通道均无法确认后重新恢复，必须撤销旧动作并重新同步；是否更换 epoch 由统一会话管理器决定，其中进程重建和明确停止后必须更换。

临时 BLE 连接丢失但 LAN 已经可用时，继续同一逻辑会话。若已进入本地独立接管，恢复必须同步 `localControlGeneration`，取消旧在线事务，先处理当前本地事务，再决定是否恢复在线协调。传输层不得终止正在执行的本地保护逻辑。

### 消息信封与接收入口

统一信封至少包含以下字段，LAN v2 与 BLE 使用相同业务语义：

| 字段 | 用途 |
|---|---|
| `protocolVersion`、`type` | 版本与消息类型，未知控制类型拒绝 |
| `coordinationEpoch`、`senderInstance` | 拒绝旧进程和旧协调会话 |
| `messageId`、`stateVersion` | 跨通道消息去重与状态单调更新 |
| `targetRevision`、`controlGeneration` | 目标和本地控制代次匹配 |
| `requestNonce`、`replyTo` | 关联一次新鲜请求与响应 |
| `transactionId`、`action` | 业务动作去重，不随通道改变 |
| `payload` | 观察、状态同步、命令、回执或地址更新 |

通道加密序号与业务 `stateVersion` 分开：前者防止该加密会话内重放，后者避免两个合法通道先后送达的新旧状态相互覆盖。样本继续携带 `instance/event`；旧事件不能因换通道被当作新起播。

`stateVersion` 按发送方实例和状态主题分别递增，完整快照与局部更新须显式区分，不能因一个诊断消息序号较新而丢弃耳机状态。已处理的相同 `messageId` 可以返回缓存回执或结果，但不得再次进入动作入口；跨通道再次发送时使用该通道的新加密记录序号，不能复用 AES-GCM nonce。

消息处理顺序为：边界与认证校验 → 会话和目标校验 → 消息去重 → 新鲜度校验 → 本地控制代次校验 → 持久化动作消费 → 调用执行器。状态、结果和执行请求进入同一业务队列；磁盘写失败时不执行硬件动作。

手机与 Mac 都使用有界的动作消费日志，键为配对身份、协调 epoch、事务 ID 和 action。记录 pending、completed、failed 或 outcome_unknown。重启后出现 pending，只重新观察硬件结果，不再次连接或暂停。至少保留当前 epoch 的全部有效消费记录；例如容量设为 256 项时，满额应安全换 epoch 并同步，不能直接淘汰仍可能重放的项。

目标是“每个动作最多执行一次”。发送后崩溃可能导致结果未知，因此不承诺严格的恰好一次执行。跨通道重发只补送同一请求或查询结果，不重新发明新事务。

## BLE 数据通道与认证

### GATT 扩展

保留既有基于 Mac pin 派生的发现 UUID 和 v1 challenge、endpoint 特征。在同一服务中追加以下 v2 特征，避免要求用户更换原有伴生关联；具体特征 UUID 在协议实现阶段冻结。

| 特征 | 属性 | 用途 |
|---|---|---|
| `capabilities` | read | 有界的协议版本与帧大小提示，不含授权信息 |
| `link_rx` | write with response | 手机发送握手、状态与请求 |
| `link_tx` | notify | Mac 发送握手、事件提示、响应与结果 |

手机发现服务后完成通知订阅，再做双向认证。未认证的 capabilities 仅决定尝试路径；最终能力集合必须包含在双方认证的握手记录中。旧手机继续读地址后断开，新手机在认证成功后保持连接。

BLE 可用性由蓝牙、应用是否允许协调和身份状态决定，与 `hosts`、TLS 端口是否存在分开。不能因旧 `endpoint.available=false` 就跳过 v2 特征。Mac 可同时报告“BLE 可协调，LAN 无地址”。

Mac 为每个 central 独立保留握手和订阅状态，只向认证通过的 central 发送其加密数据。一个已绑定手机只允许一个活动 BLE 控制连接，可同时保留一条 LAN 路径；BLE 连接替换必须重新证明同一身份。未认证握手最多同时两个，每个十秒截止；超出限额的新请求直接拒绝，不挤掉已认证连接。

升级后每次重新连接都发现服务并核对特征版本。GATT 缓存变化必须通过正常服务发现与公开平台机制处理；缺少 v2 特征时回退兼容模式，不调用隐藏的缓存刷新 API。将“升级后仍看到旧服务表”列入实机验收。

### 复用长期身份建立短期密钥

默认不把操作系统蓝牙 bonding 当作身份根，也不要求为本功能执行 `createBond()`。BLE 业务内容采用应用层认证加密，未通过认证的链路不得传递控制、目标地址或播放详情。

拟定握手如下，最终字节编码、算法标识和测试向量在实现前固化：

1. 手机发起 ClientHello，携带已绑定 client ID、本次进程实例、随机 nonce、临时 P-256 ECDH 公钥和支持的能力集合。
2. Mac 返回自己的身份公钥、本次 nonce、临时 ECDH 公钥、进程实例和能力选择，用原 Keychain 身份签名覆盖完整握手上下文。
3. 手机将 Mac 公钥重建成标准 SPKI，核对已保存 pin，再验签；手机用原 Keystore 身份签名同一握手上下文，Mac 用 `peer.json` 中的手机公钥验证。
4. 双方由临时 ECDH 共享秘密，经 HKDF-SHA256 导出两个方向独立的 AES-GCM 密钥、nonce 前缀及密钥确认材料；互发 Finished 后才允许进入状态同步。

签名上下文使用独立域 `SoundLink/link/v2`，绑定协议、算法、双方身份、角色、nonce、临时公钥、进程实例与所选能力，防止跨协议复用或篡改协商。原长期密钥只负责签名；Android 当前密钥只有 SIGN/VERIFY 用途，不将其改成 ECDH 密钥，也不导出私钥。

每个加密方向使用独立密钥和递增 64 位计数器；96 位 AES-GCM nonce 由该方向导出的 32 位前缀与计数器组成。协议头纳入附加认证数据。序号回退、重复、溢出或认证失败不进入业务队列。断开后重新握手，旧密钥和计数器不恢复；密钥仅在内存，最长使用 15 分钟或任一方向达到 2²⁰ 条记录即更新。Mac 提前发出更新提示；若手机深睡延后处理，到期后只接受重新握手，不延长旧密钥有效期。更新传输密钥不改变仍有效的逻辑 epoch，且旧事务的期限继续计时。

以上是待实现的协议选择，使用平台密码库，不自行实现密码算法。HKDF 与认证加密各有公开标准，但这些标准不等于已经审查了本产品的握手组合；跨端测试向量和协议安全审查是控制功能启用的前置验收项。[RFC 5869](https://www.rfc-editor.org/rfc/rfc5869)、[RFC 5116](https://www.rfc-editor.org/rfc/rfc5116)

### 分片与流控

统一消息使用紧凑 UTF-8 JSON，再封装为认证加密记录并分片。控制记录上限建议 4 KiB，普通状态应尽量小于 1 KiB；名称和诊断长文本截断或只在 LAN 拉取。分片头包含记录 ID、总长、片号和片数，整体认证成功前不解析业务内容。

按实际 MTU 和 Mac 的通知长度上限发送，必须支持 ATT MTU 23 的最小场景，不能假设请求 247 就实际获得 247。Android 新版本对 MTU 请求有额外行为，实际结果以回调为准。[Android BluetoothGatt](https://developer.android.com/reference/android/bluetooth/BluetoothGatt#requestMtu(int))

每个 GATT 客户端只串行进行一个写入或描述符操作；Mac 通知发送遇到缓冲已满时停止排队，等待可写回调。通知被平台接受不算手机业务已收到，另用应用层 ACK。Apple 提供通知订阅、发送以及恢复发送的回调。[Apple GATT 外设流程](https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/PerformingCommonPeripheralRoleTasks/PerformingCommonPeripheralRoleTasks.html)

每个对端建议最多四个待组装记录、16 KiB 总缓冲；组装期限三秒，且受业务剩余期限约束。握手单独允许十秒总预算。过长、冲突分片或持续无效输入关闭该次会话。最新状态可以合并覆盖旧的待发状态；控制请求、结果、暂停与撤权不能被诊断数据挤掉，也不能无限排队。

## 命令时效与双向推送

### 推送先通知有变化，再取得新鲜执行授权

不直接把现有 HTTP 响应中的 `ttlMs=5000` 原样放进主动通知。通知可能在系统队列里停留数十秒，手机晚收到后从零计五秒会执行过期指令。两端单调时钟也不能直接互减。

采用“事件提示 + 带随机挑战的即时交换”：

1. Mac 起播后立即通过 BLE 发出 `EVENT_AVAILABLE`，包含事件和事务标识；它只提示需要同步，不授权硬件动作。
2. 手机收到后立即发 `SYNC_REQUEST`，带新的随机 nonce、当前目标、本地控制代次和新采样状态，记录本机单调起点。
3. Mac 收到后重新校验双方状态、原事件及事务期限，返回匹配 nonce 的 `SYNC_RESPONSE`；只有仍有效时才附带命令与服务端剩余 TTL。
4. 手机扣除本次完整 RTT 和本地排队时间后执行，且再次检查当前本地条件。回复最多使用一次，不能接受另一次交换的 nonce。

有效预算为 `min(5000, ttlMs) - exchangeRTT - localQueueDelay`，非正值直接拒绝。完整 RTT 是保守扣除值，不是单向网络延迟。Mac 五秒事务期限不因提示重发、换通道或重新拉取而重置；事件提示迟到时只返回当前状态或“已过期”。

本端 TTL、队列等待与握手期限都使用包含深睡时间的单调时钟：Android `elapsedRealtime`，Mac 现有 `MonotonicTime` 所用的 `mach_continuous_time`。休眠期间不能暂停倒计时；进程重建后也不能恢复旧倒计时并继续执行。

手机起播同样立即发事件提示与状态。Mac 若要据此发起动作，先向手机发本次新随机挑战，手机在收到挑战后重新采样并响应；Mac 以匹配响应、采样年龄及本次 RTT 判断新鲜度。未经新鲜度确认的主动状态可以更新历史展示，不能独自触发远端动作。LAN 请求响应可承载同样的挑战流程。

### 确认与回退

应用层 ACK 表示消息已验证并接收；只有执行结果和真实音频路由验证才能表示交接成功。写入回调、GATT indication 确认或 HTTP 200 都不替代硬件结果。

关键消息等待应用层确认的初值为 1.5 秒。超时后若另一条通道已认证且有剩余预算，使用相同事务 ID、同一 action，通过新 nonce 查询当前状态和剩余授权；旧通道晚到的响应由消费日志和会话检查拒绝重复执行。备用通道冷启动时不保证能赶上本次五秒期限。

两条通道都失去确认后再恢复，先进行 `stateSync`，消费恢复时已有的播放基线；不补做离线期间累积的播放或暂停。只发生通道切换、逻辑会话始终连续时不重置正常事件水位，避免吞掉切换瞬间的新事件。

## 锁屏运行策略

### 生命周期与执行线程

Android 延续伴生服务和 connectedDevice 前台服务。伴生服务接收在场与恢复入口；前台服务承载用户已启用的持续设备通信及播放观察，显示可停止的通知。Android 官方将伴生服务或 connectedDevice 前台服务列为持续监听 BLE 通知的路径，但进程终止会关闭连接，后台启动仍受限制。[后台 BLE](https://developer.android.com/develop/connectivity/bluetooth/ble/background)、[前台服务类型](https://developer.android.com/develop/background-work/services/fgs/service-types)

实现上分离 BLE I/O、LAN I/O 和业务串行队列。BLE 回调快速校验并投递，不等待 HTTP、UI、日志落盘或耳机连接完成；LAN 有独立超时和取消。硬件执行器保持现有有界执行与路由确认流程。

持续连接期间使用事件驱动的播放与设备回调。只读采样定时器用于运行时补充，不能把定时器预计执行时间作为锁屏保障。Mac 发送事件后，手机是否在不亮屏的情况下收到回调、完成认证检查并回复，是需要测量的主指标。

### 空闲与活跃的不同策略

| 状态 | BLE 与 LAN 行为 | 状态显示与执行条件 |
|---|---|---|
| 活跃播放或交接 | 变化立即发；有工作时每三秒可合并一次状态校验 | 仍以执行前新鲜交换为准 |
| 双端空闲且 BLE 已验证 | 保持订阅；Mac 每 30 秒最多一次应用层探测，手机收到后回应；不额外维持 LAN 三秒轮询 | 展示最近确认时间；底层连接未断但探测超时则显示待确认 |
| BLE 待确认 | 最多追加一次有界探测，同时检查 LAN；失败转事件等待 | 不用旧状态授权远端动作 |
| LAN 单独可用 | 保持现有约三秒请求响应与事件立即上报 | 明确标示锁屏下行可能延迟 |
| 两条都不可用 | 仅有界恢复及已授权的本地观察 | 远端状态显示为历史 |

30 秒探测是初始耗电实验参数，不是不断续期的控制租约。若测得探测显著增加待机耗电，可延长至 60 秒或只在有事件时验证；无论何种间隔，动作前的新鲜度检查不能省略。最近设备状态超过十秒仍按过期处理，保留现有使用会话规则，不能用“BLE 在线”延长旧样本寿命。

同时需要调整本地失联策略的输入：不能继续单凭“十秒未收到周期心跳”就认定整体失联，否则 30 秒空闲探测会让本地策略误入独立接管。新起播发生时，若通道尚存在但状态已旧，先发即时同步，在本次事件预算内最多等待 1.5 秒；两条通道均无有效确认后，才按原有授权和使用会话条件评估本地失联动作。探测等待计入同一动作期限，不重新获得五秒。确知两条通道均不可用时可直接评估本地策略。这样只改变通信证据的输入，不放宽耳机控制条件。

### 唤醒锁与系统边界

沿用当前事务内的短时唤醒锁与静音恢复保护，不增加常驻锁。可以评估收到真实 BLE 事件后、从校验到回执之间最长两秒的短锁，结束即释放；握手失败、取消和异常也要释放。这只能保护已经进入应用的处理窗口，不能让尚未收到的回调出现。

Doze 会延后 CPU 和网络活动，普通唤醒锁也存在限制。因此“前台通知常驻”“锁已获取”“连接未断”都不构成深睡实时性保证。默认不新增电池豁免要求；默认设置和用户主动授予豁免的结果分别报告。[Android Doze](https://developer.android.com/training/monitoring-device-state/doze-standby)

Mac 真正睡眠、关机或退出时不能承担实时协调。睡眠前发送不可用消息只是尽力而为，手机仍需通过无确认降级；唤醒后重建发布与认证，再同步当前状态，不重放睡前事务。合盖但外接显示器保持唤醒与真正睡眠分别验收。

手机强行停止、用户主动停止前台服务、撤权、重启后首次解锁前，是独立边界。强行停止后不承诺自动拉起；首次解锁前不承诺访问原有凭据和偏好。划掉最近任务与强行停止必须分开测试。

## 自动重连与网络切换

### 恢复调度器

持久保存 `auto_enabled`，内存管理每条通道的连接代次、进行中的任务、失败次数和下一次允许尝试时间。所有恢复入口只提交“恢复意图”，由同一调度器去重；不允许 CDM、PendingIntent、网络回调同时创建多条 GATT 连接。

| 事件 | 调度器动作 |
|---|---|
| 已知设备在场或过滤广播命中 | 有新设备句柄时有界连接，认证后再认定身份；BLE 地址不是信任凭据 |
| BLE 断开或业务探测失败 | 取消该代次未完成操作，尝试 LAN；进入 BLE 有界恢复 |
| 手机网络可用或链路属性改变 | 只刷新 LAN 候选并验证；BLE 正常时不取消逻辑会话 |
| Mac 地址改变 | 更新旧地址描述，并通过已认证 BLE 发送地址候选 |
| Mac 蓝牙重新就绪或系统唤醒 | 重建服务与广播，等待认证；不得恢复旧动作 |
| 手机开机、应用覆盖升级或蓝牙重新开启 | 首次解锁及权限允许后重新登记系统入口，遵守已保存的暂停状态 |
| 用户主动暂停 | 持久保存暂停，取消扫描与连接尝试，关闭两条控制通道 |

直接连接每次最多十秒，完整发现流程最多 25 秒；重试间隔建议 1、2、4、8、16、30 秒并加入约 20% 随机抖动。一次主动恢复窗口最多 75 秒，窗口内所有尝试共用这个上限，不因重复回调无限重置。用户显式重试可以启动新窗口。

窗口结束后停止主动扫描循环，保留系统在场与过滤广播入口。已经连接但应用层无确认时先做有界探测，再关闭失效 GATT；不能只等待 FIRST_MATCH，因为设备始终在范围内时未必再次产生首次发现事件。新系统事件只有在状态变化或冷却满足时才开启下一轮恢复，建议最短冷却 30 秒。

本机新的播放意图、用户打开 App 或手动重试也可以触发一轮有界恢复；后台媒体回调只有在本地观察仍合法存活时才是可用入口。若进程已退出、设备一直在附近且系统没有再次投递发现或在场事件，恢复可能等到下一次系统事件或用户打开 App；不把这个空窗描述为必然自动恢复。P0 必须专门测试该条件，必要时评估平台允许的重注册方式，不能靠无限定时扫描补齐承诺。

默认对新扫描结果使用 `autoConnect=false` 的有界连接，便于准确控制超时和资源释放。`autoConnect=true` 可作为后续机型实验，但不能作为唯一恢复入口：它依赖仍存在的客户端对象与设备句柄，无法解决进程死亡及随机地址变化。Android 文档明确说明 CDM 对随机 MAC 有限制。[Android BLE 连接与后台恢复](https://developer.android.com/develop/connectivity/bluetooth/ble/background)

### 从公司到家的一次完整过程

1. 两台设备离开公司 Wi-Fi。LAN 失效；若 BLE 仍正常，业务会话和当前目标保持，用户无需操作。
2. Mac 接入家里网络并更新地址，通过认证 BLE 提供新的 LAN 候选。手机尚在移动数据也可继续 BLE 协调。
3. 手机接入家庭 Wi-Fi 后验证候选：固定 Mac pin、手机签名认证都成功才保存新地址。BLE 收到候选不等于局域网已可达。
4. 若途中 Mac 合盖睡眠，手机转入不可协调或既有本地失联行为；Mac 唤醒后由发现入口重连，先同步再接受新起播。

LAN 路径监听实际可用网络及链路属性，不能只依赖默认网络：无互联网的 Wi-Fi 也可能能访问 Mac，而默认网络可能仍是蜂窝网络。新版 LAN 连接按获准的候选网络建立，仍保留固定身份校验。Android 17 的局域网权限单独检查，拒绝 LAN 不应主动关闭仍获准的 BLE；同一权限组撤销可能同时影响多项授权，应重新查询实际权限。[Android 局域网权限](https://developer.android.com/privacy-and-security/local-network-permission)

现有 IPv4 私有地址候选与扫码更新继续有效。本阶段不把 Bonjour 或全子网扫描变成必要条件；BLE 不可用且 Mac IP 已变时，LAN 地址自动找回仍可能受限，保留扫码更新入口并如实提示。

## 现有配对保留与升级兼容

### 保留清单

| 现有记录 | 迁移规则 |
|---|---|
| Mac Keychain `app.soundlink.mac.identity.v1`、证书、公钥 pin 和设备 ID | 原样使用；新增 BLE 不改身份、不轮换证书 |
| Mac Application Support 中 `peer.json` | 保留原 client ID、公钥、绑定信息；不强制改写成新格式 |
| Android Keystore `soundlink.identity.v1` 与 `client_id` | 原样使用；需要证明身份时在 Keystore 内签名 |
| Android `soundlink` 偏好中的 `peer`、pin、地址 | 原样读取；地址仅是可更新路由，不是重新配对条件 |
| Mac 伴生 `association_id`、`association_pin` | 保留；只有系统关联实际缺失时才提示重新授权 |
| 耳机目标 revision、双端地址映射、耳机控制关联与开关 | 保留且重新核对，不因新通道默认增加控制权限 |
| 自动恢复开关、用户暂停、失联失败锁和恢复标识 | 保留；升级不能自动解除暂停或失败锁 |
| LAN token、BLE 临时密钥和旧事务 | 不迁移为永久凭据；进程重建后重新认证和同步 |

新字段放在独立的 `transport-v2` 配置区域或新偏好键，采用可重复、原子提交的版本化初始化。先只读旧记录，验证长期密钥确实存在、身份与记录一致，再保存新增字段。初始化失败保留 v1 原样可用；不删除旧配置，不把“读取失败”当作生成新身份的理由。

Android 当前 `keys()` 在 alias 缺失时会生成密钥。迁移路径必须先区分“全新未配对安装”和“已有配对但密钥缺失”：后者停止自动迁移，明确显示身份无法恢复，不能静默生成新密钥冒充原手机。Mac 钥匙串暂时不可访问同理，应等待恢复访问。

两端保持原应用标识、Android 包签名，以及 Mac 的钥匙串访问条件。卸载清数据、换签名安装、删除 Keychain/Keystore 私钥或用户解除配对，不属于无损升级；此时需要重新建立信任。普通锁屏下使用现有身份应单独验证，避免新代码引入每次解锁或生物识别要求。

### 不同升级顺序

| Mac | Android | 预期 |
|---|---|---|
| 旧版 | 新版 | 使用 v1 LAN；没有 BLE 控制特征时显示对端未支持，原配对不变 |
| 新版 | 旧版 | 继续提供旧 GATT 地址特征及 v1 HTTPS，保持旧行为 |
| 新版 | 新版 | 可以直接通过既有身份认证 BLE v2，无需先成功访问 LAN |
| 回滚到旧版 | 任意 | 保留旧记录可读；重启后仅按可协商的协议恢复，不重放 v2 命令 |

新增经认证的能力查询与 v2 会话建立接口，建议为 `/v1/capabilities`、`/v2/link/session`、`/v2/link/exchange`。旧 Mac 的已验证 HTTPS 404 表示该接口不支持；网络超时或未认证 BLE capabilities 不足以证明版本不支持。

LAN v2 在原固定身份 TLS 和手机认证上加入逻辑会话，不降低 TLS 检查。BLE 能力协商纳入签名握手。双方确认 v2 生效后，来自该手机的 v1 ping 不得再驱动第二套控制状态机，可以拒绝控制或仅用于兼容诊断。退回 v1 必须先撤销 v2 事务并建立新基线，不能在同一事务内混用两版命令。

为支持新旧版本共存，业务适配器必须能将 v1 的请求响应和 v2 消息都映射到同一个权威状态机。新增格式只在明确协商成功后发送；不能先破坏旧端，再要求用户两端同时升级。

## 用户可见状态与诊断

主界面显示“已连接 · 蓝牙”“已连接 · 局域网”“蓝牙连接待确认 · 正在尝试局域网”“已配对 · 等待设备”或“已暂停”。连接状态和耳机控制授权分别显示；LAN 不可达但 BLE 工作时不得展示整体离线。

诊断详情至少包括：当前业务模式、双方版本、逻辑 epoch 的匿名标识、每条通道的连接及认证状态、最近应用层确认年龄、恢复入口、队列等待、分片数、当前 MTU、协议错误、事务结果，以及发送失败与系统调度迟到的区分。

沿用现有进程 UUID、boot count、elapsedRealtime/uptimeMillis 和测试标记。新增 `ble_notify_enqueued`、`ble_callback_received`、`message_verified`、`app_ack_received`、`route_fallback`、`state_sync_done`、`duplicate_rejected` 与 `stale_command_rejected`。同一消息和事务跨两端可关联，但日志不记录密钥、完整身份、会话 token 或媒体内容。

延迟按同一端的往返计时报告；手机回调到执行另用手机时钟计时。跨端精确单向延迟需时钟映射及误差范围，不能直接相减墙钟。ACK 丢失但稍后确认已收的样本单独列出，不能把所有无 ACK 都算成未送达，也不能从成功率中删除超时样本。[现有锁屏诊断方法](lockscreen-diagnostics.md)

## 验收门槛与测试矩阵

以下数值是拟定的工程验收目标，不是当前性能承诺。先验证 BLE 息屏消息，再接硬件控制；未通过时保留 LAN 兼容，双通道控制不进入默认开启状态。

### 分层验收目标

| 项目 | 目标与统计方法 |
|---|---|
| 已连接 BLE 的息屏消息往返 | 每个重点组合、每个方向至少 100 次；应用层确认 p95 ≤ 500 ms、p99 ≤ 1500 ms，1500 ms 内成功率 ≥ 99%；超时进入失败计数 |
| 长空闲后首个事件 | 分别空闲 1、5、15、30、60 分钟及八小时；区分冷首包与连续探测数据，不用后续快包掩盖首包失败 |
| 已有热备时通道回退 | 故障到另一条通道有效确认 p95 ≤ 3 秒；事务原五秒期限不改变；LAN 息屏不达标则标明该组合不支持实时回退 |
| 息屏离开再返回 | 每个重点组合至少 30 次；从独立记录的重新进入范围到 stateSync 完成，p95 ≤ 15 秒，30 秒内成功率 ≥ 95%；超过 30 秒为失败 |
| 完整交接 | 每个方向至少 30 次，在原五秒期限内报告成功或明确失败；分别统计媒体路由成功与静音恢复，不以传输 ACK 代替 |
| 安全与一致性 | 旧命令、重复动作、错误身份、错误目标及控制代次均不得触发硬件；任何一次误执行都阻止发布 |
| 配对保留 | 两种升级顺序、无 LAN 升级后连接、重启、回滚各至少五轮；正常覆盖升级零次要求重新扫码，所有原授权和暂停状态保持 |
| 待机耗电 | 同设备相同条件做至少三组配对八小时测试，对比关闭自动协调的基线；拟定增量中位数 ≤ 2 个电量百分点，报告单组差异和测量分辨率 |

如果采用短锁或 30 秒探测才能达到延迟目标，必须同时通过耗电门槛。冷首包测试另设无周期探测的诊断模式，确认性能是否依赖定期唤醒；该模式结果与产品默认模式分开报告。

### 必测组合

| 类别 | 场景 | 关键判据 |
|---|---|---|
| 基础通道 | 同网双通道、仅 BLE、仅 LAN、两端无 Wi-Fi、不同 Wi-Fi、手机移动数据 | BLE 模式无需 LAN 即可完成认证、目标同步、协调和回执 |
| 锁屏 | 后台亮屏、锁屏短待机、长静置、深睡、划掉任务、省电模式 | 不亮屏、不打开 App 也能记录回调与完成往返；失败明确归类 |
| 方向 | 手机耳机按键起播、Mac 起播、双端接近同时起播 | 两个方向分别统计；冲突保守处理，无重复抢占 |
| 共存 | AirPods 音乐播放、通话保护、其他 BLE 设备、Mac 其他广播 | 不破坏音频；保持现有通话保护；记录丢包和音频异常 |
| 换网 | 公司到家、DHCP 地址变化、无互联网 Wi-Fi、VPN、多网卡、AP 隔离 | BLE 正常时不整体离线；LAN 恢复先认证后更新地址 |
| 蓝牙恢复 | 两端分别关开蓝牙、出范围再返回、Mac 地址变化、通知订阅失效 | 无连接泄漏；重新发现、订阅、认证、同步依次完成 |
| 生命周期 | Mac 真睡眠与唤醒、菜单栏后台、正常退出重开、手机进程回收、重启首次解锁 | 原配对保留，旧 epoch 和旧事务无效；强行停止按产品边界处理 |
| 权限 | 蓝牙、LAN、伴生关联分别撤销与恢复 | 拒绝的通道停止；其他有效通道按实际剩余授权继续；不后台弹授权页 |
| 故障注入 | 分片丢失、乱序、重复、MTU 23、通知队列满、HTTP 阻塞、迟到 30 秒 | BLE 不被 HTTP 阻塞；迟到消息不重获 TTL；内存与重试有界 |
| 双通道竞争 | A、B、A 命令乱序、执行后 ACK 丢失、动作前后进程终止、回退时原通道恢复 | 每个 action 最多执行一次，结果未知时只读验证 |
| 本地失联 | 本地接管中恢复另一通道、失败锁后收到旧连接样本、目标改变 | 控制代次生效，失败锁不能被旧证据解除 |
| 升级安全 | 原身份缺失、Keychain 暂不可读、GATT 服务缓存、仅单端升级、回滚 | 不静默换身份、不混用两套控制状态机、不删除旧绑定 |

默认 ROM 配置为主验收组，厂商后台设置或电池豁免另列。正式锁屏测试关闭无线调试、拔 USB，关闭通知亮屏，并记录充电、温度、网络、系统版本和电池策略。可以用 ADB 强制 Doze 或故障注入做开发诊断，但不能将这些结果替代无调试条件下的自然深睡验收。

机型从当前手机与 Mac 开始，再覆盖至少一个接近原生 Android 的设备和一个不同厂商后台策略的设备；若暂时没有设备，只能发布已有验证组合的结论。Mac 也需记录机型、芯片和系统版本，不从单机推断全部 Mac。

## 实施顺序与完成条件

| 阶段 | 未来实现内容 | 进入下一阶段的条件 |
|---|---|---|
| P0 锁屏可行性 | 在原 UUID 下建立持久 GATT、认证、只读事件与应用层回执；不驱动耳机 | 仅 BLE、默认省电、长息屏双向首包与稳定往返通过；明确回收恢复与耗电表现 |
| P1 统一业务入口 | 分离 LAN/BLE I/O，增加逻辑 epoch、nonce 新鲜交换、消费日志与模拟时钟测试 | 双通道乱序、过期、崩溃恢复和本地控制代次测试通过；安全握手审查完成 |
| P2 控制与兼容 | 接入同一耳机执行器，新增 LAN v2，保留 v1；完成覆盖升级与回滚 | 双向交接、原配对保留、原暂停与失败锁保留、新旧版本矩阵通过 |
| P3 自动恢复 | 统一系统入口、有限退避、网络候选、服务缓存和生命周期恢复 | 换网、离开返回、睡眠唤醒、蓝牙重开与权限矩阵通过 |
| P4 默认启用 | 在已通过的设备组合启用 BLE 优先，保留诊断性的 LAN 模式开关 | 延迟、正确性、恢复和耗电门槛全部通过，限制写入发布说明 |

协议编码、特征 UUID、容量和计时参数在 P0/P1 固化为跨端公开测试向量。即使 BLE 连接能够保持，若目标手机的深睡通知不能及时进入应用，P0 仍判定失败；先定位平台行为和授权条件，不以延长在线阈值、长驻唤醒锁或重复扫描掩盖。

落地时主要新增传输与会话模块，并调整 `ConnectionService`、`MacDiscovery`、`Recovery` 及业务适配入口。原配对密钥、耳机控制 API 和产品授权不需要更换；原有五秒期限和保护规则继续约束所有通道。该设计不把传输可靠性改进等同于耳机硬件切换必然成功。

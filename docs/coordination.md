# Sound Link 耳机流转规则

设计更新：2026-10-15。新起播优先，目标端直接连接优先，来源端暂停尽力而为。实时心跳不是耳机使用会话本身。

当前已接入双向实际连接与尽力暂停；0.4.8 改为按使用会话失联接管、失败阻止和当前状态同步。Mac 正常退出主动归还仍未实现。历史版本小节只说明对应版本，当前行为以下面的使用会话规则、0.4.9 期限修订及 0.4.10 手机独立接管为准。

## 状态与不变量

协调服务只控制用户选定的一副耳机。每条状态携带目标 ID、目标版本、进程实例与会话 ID，并记录本地单调时间。

| 状态 | 条件 | 行为 |
|---|---|---|
| Disabled | 用户停止、撤权或解除配对 | 撤销该功能的扫描/观察和监听，不自动恢复 |
| Standby | 已配对，电脑明确退出或协调会话结束 | 无媒体干预；仅保留允许的系统发现入口 |
| Verifying | 发现 Mac，正在认证、同步目标和新基线 | 不进行耳机动作 |
| WaitingForHeadphones | 双端状态新鲜，目标耳机都明确断开 | 不因媒体播放连接；等待真实连接事件 |
| Coordinating | Mac 参与、目标一致，有有效的耳机使用证据 | 新起播端提出接管；不要求对端先暂停或释放 |
| Handoff | 有有效目标和新事件的唯一交接事务 | 目标端连接优先、验证路由，再尽力暂停来源端 |
| Exiting | Mac 正常退出，冻结普通切换 | 有限归还后进入 Standby |
| Degraded | 目标不同、权限不足、状态未知或能力受限 | 无新自动动作；显示具体原因 |

未知不等于断开。Handoff 期间出现短暂双断开由同一事务管理，不重新开始另一轮连接。用户停止优先于自动恢复。重连、开盖、更换目标后都建立基线，不把已持续播放当作新事件。

## 按方向保护耳机占用（2026-10-27）

自动切换保护当前持有耳机的来源端：来源端有输入、通话或受保护音频时，不因另一端播放而抢占。目标端本地的输入/通话标记不再是全局禁令；目标端仍需状态可读、合格的新播放事件、有效目标与授权。单独出现输入流、佩戴耳机或解除保护不产生接管事件。Android 当前仍只从已有媒体/游戏用途生成起播事件，本次不新增电话或佩戴检测。

`audioReadable` 将无法读取音频状态与真实输入活动分开；任何一端状态不可读时均不启动在线自动切换。旧客户端缺少此字段且 `protectedAudio=true` 时仍保守处理，不猜测保护来源。失联接管沿用来源端最后可信保护状态、使用会话和失败锁；仅移除目标端已确认输入造成的阻止。

Mac 对输入进程读取 input scope 的设备列表。只有聚合设备明确存在 AudioTap、且全部可读活动子设备均没有输入流时，才将其视为系统播放采集并排除保护；普通/虚拟麦克风、混合输入以及信息不完整仍保护来源端。不按 `corespeechd` 或其他进程名字放行。诊断记录 `audioReadable`、输入进程/PID、设备及分类，不录音。

手动“耳机切换到此 Mac”代表明确意图，不因两端输入保护而禁用；仍保留目标变更、用户取消、并发交接和手机独立事务检查，最多执行一次有界连接，不发送旧端暂停。自动接管后的旧端暂停仍检查来源端保护、新事件与状态有效性。

## 两端如何监听播放

Android 由 `connectedDevice` 前台服务持有播放观察和通信，Activity 只展示状态。短暂心跳过期只影响远端状态新鲜度，不立即撤销本机只读观察；手机用户停止、控制撤权或服务结束时停止；网络重试用尽不再直接结束有使用会话的观察。当前没有新增常驻唤醒锁。通过 `AudioPlaybackCallback` 和活跃播放配置得到候选变化；它不是麦克风录音，也不是“声音还没发出”的系统级拦截。不能据此承诺全局提前静音或准确识别每个播放器身份。[AudioManager](https://developer.android.com/reference/android/media/AudioManager#registerAudioPlaybackCallback(android.media.AudioManager.AudioPlaybackCallback,%20android.os.Handler))。

先验证普通应用实际可见的用途、变化和设备信息，再决定分类规则。只用活跃数量会漏掉“一端持续有播放时另一播放器开始”的变化，也可能被短视频换集误触发。通知过滤、通话/会议保护、静音视频、网页和后台音乐必须逐项测；未知类别不启动普通抢占。缺少可靠通话保护信号时，不把该场景标为已支持。

Mac 媒体观察经平台适配器输出同一候选事件模型，优先采用可分发的公开 API。旧 MediaRemote Adapter、音频保护探针不直接进入产品依赖；事件来源的覆盖范围与发布条件必须独立验证。播放观察能力不足时保持受限状态，不偷偷启用 ADB 或私人接口兜底。

## 普通自动交接

1. 用户启用，电脑仍参与协调，目标映射一致；以本机实际连接及有效的耳机使用记录确定资格。双端明确断开时不连接；未知不冒充断开。手机失联时可依下文 0.4.8 的使用会话授权单次本地接管；无固定时间到期，失败后等待新的连接证据。
2. 新起播端优先于旧端正在播放的普通音乐。手机新媒体/游戏可以接管 Mac 音乐，Mac 新合格媒体可以接管手机音乐；Android 继续筛选媒体/游戏用途；Mac 按当前通用新输出规则，通知、提示音也可能触发。通话/会议保护、用户停止及失败退避仍优先；显式外放意图识别暂缓。
3. 起播端根据唯一事件 ID、目标版本、会话与期限尝试一次直接连接，Mac 失联接管不要求对端实时在线；手机当前仍需要 Mac 在线下发认证命令。两端都不等待来源端先暂停或主动断开。动作入口须能确认当前本机保护状态与有效使用资格；在线时检查对端保护；失联时按下文有限风险规则处理，不能宣称已排除对端通话。
4. 先验证目标端 profile 和实际路由，再处理来源端暂停。连接请求返回成功不等于交接成功。直接接管不受支持时，记录该型号能力限制；来源端协作释放可作为单独验证的兼容路径，不把无限等待当作默认交接。
5. 已存在的持续播放、连接改变、心跳恢复和播放器恢复状态不生成反向抢占。只消费新的有效媒体边沿；重复事件、过期事件、旧目标/会话均拒绝。双端同时新起播只允许单个有限事务；尚不能可靠仲裁时不执行，避免争抢。
6. 连接失败/超时停止本轮，保持明确失败并进入冷却，不自动循环连断。暂停失败不撤销已经成功的耳机接管，也不触发反向连接。

### 来源端暂停：尽力执行，不阻塞交接

先让系统/播放器响应蓝牙路由丢失；如仍播放且存在已授权、可准确定位的旧媒体会话，再最多发送一次明确的 `pause`。不得使用 play/pause 切换键，避免把已暂停的音乐重新播放。

暂停指令绑定交接 ID、目标版本、来源设备、原播放会话/事件、单调期限。执行时必须确认该会话仍是旧播放、未重新持有耳机、没有用户后续播放意图；已暂停、权限不足、会话无法确认、离线或超时就跳过。迟到指令不补做；不能暂停用户后来启动的其他播放器。成功接管后不主动恢复旧端播放，不调整系统音量。

系统并不保证所有 App 在耳机断开后暂停。Android 会通知音频路由即将变为扬声器，播放器需要自己处理；因此仍须验证音乐、浏览器视频等是否短暂外放。Android 定向控制其他媒体会话需要适用授权；0.4.0 提供可选通知使用权入口以获取媒体会话；不读取或保存通知内容。未授权时跳过主动暂停。Mac 暂停适配也须逐播放器验证，不能暗中接入私有 API。无可靠能力时跳过正是 best-effort 约定的一部分。

### 0.3.3 观察实现的边界

- 10 秒心跳新鲜度继续用于在线显示和已验证候选，不再决定 Android 本地观察是否立即停止。
- 相同目标和观察实例保留已消费事件序号。重连时仅接受新序号且 `eventAgeMs < 8 秒` 的手机起播；旧序号、旧事件、冷启动基线不重放。显式 Mac 暂停/退出或目标/实例变化仍建立新基线。
- Mac 起播而手机过期时，最多参考 120 秒内目标一致、曾连接手机且未报告受保护音频的样本，显示“手机 → Mac（待验证）”；该样本不代表当前仍连接/无通话，不授予硬件权限，候选 8 秒失效。窗口参数只是取证起点。
- 没有证据时不为改善界面假造在线；新旧两端同时播放普通音乐不是拒绝候选的理由。

多点耳机可能双端同时连接；连接数不能确定音频归属，未验证的型号仍保持受限。

## Mac 正常退出与意外失联（当前行为与待实现目标）

当前：Mac 取消事务、清空本地会话并停止参与；手机收到 MAC_UNAVAILABLE 或连续请求失败超过约 75 秒后暂停网络轮询；仍有授权及可信使用会话/失败锁时保留本地播放观察，否则结束服务。计时和清理受系统调度限制。尚无主动归还命令。

以下是未实现的正常退出归还目标，不代表 0.4.9 已支持：正常合盖、休眠、退出 App 时先进入 Exiting，拒绝新普通事务，尽力通知手机。先确认手机有新鲜的接收能力与退出窗口，再释放 Mac、发出绑定旧 epoch 的一次性归还命令。手机验证目标和期限后最多尝试一次；不顺带启动播放器。

| 退出时现状 | 动作 |
|---|---|
| 仅 Mac 连接，手机近期可接收 | 尝试归还；确认超时仍停止协调 |
| 仅手机连接 | 保持手机，不发连接/断开 |
| 两端都明确断开 | 直接结束，不归还 |
| 两端都连接 | 仅在确认不会打断受保护业务时结束 Mac 占用；不反复断手机 |
| 手机不可达、状态未知或过期 | 不盲目释放后再无限尝试；停止协调 |

正常退出的等待必须短且有上限，不能无限阻止睡眠/关机。突然断电、服务崩溃或网络丢失走租约失效，不根据旧记录补做抢连；“失联补偿归还”不作为默认策略。

Android 当前在服务结束时撤销播放观察和交接验证；服务恢复后重新采样并检查命令身份、目标与剩余期限，不补做过期命令。已存在全局媒体流短时静音保护，其恢复边界见 0.4.6 小节。0.4.10 已拆分网络轮询与本地观察生命周期，规则见下文。

## 暂定参数

这些是实现起点，不是已经满足的服务保证；以统一协议配置和真机数据调整。

| 参数 | 起点 |
|---|---|
| 状态传输 | 手机约 3 秒 HTTPS ping，变化触发快速 ping；Mac 状态随响应返回，无独立 2 秒主动下行 |
| 在线指示/实时样本有效期 | 10 秒；不等于观察生命周期或耳机使用会话 |
| 耳机使用会话有效期 | 无固定时限；双端明确断开、协调结束、目标变化等事件结束会话 |
| 失联接管失败 | 锁定后续失联尝试，等待失败之后的新连接确认；不靠冷却计时解锁 |
| 恢复快照 | 仅同步当前状态、建立基线；不补做快照中的播放 |
| 正常退出的通知与释放预算 | 不超过 3 秒，具体受 OS 可用退出窗口约束 |
| 普通交接事务总期限 | 5 秒（含连接与路由验证；手机扣除通信及排队耗时） |
| 归还连接请求 | 未实现；原退出协议草案的参数不用于当前普通交接 |
| 失败冷却 | 10 秒，并要求新的合格事件 |

时间以各端单调时钟为准，不直接比较两台设备的 wall clock。当前恢复会重新采样并建立观察基线，不以长调度空白本身强制重新认证。手机认证 token 有效时复用；无 token、客户端到期或 ping 失败使 token 失效后，再通过挑战建立新认证会话。服务端 token 有效期 900 秒，客户端提前按 840 秒更新。每轮 ping 校验 nonce/epoch，动作 TTL 扣除通信和排队耗时；状态恢复不等于重新握手。

## 更换耳机

UI 展示两端系统名称及可区分的标识。新耳机需两端系统配对、Android 伴生授权；先暂停协调，再以 `expected_target_revision` 提交更改，Mac 持久化并切换目标版本/epoch，手机确认一致后恢复。中断结果不明时查询当前版本，不擅自沿用旧目标。

不同平台看到的同一耳机地址不一定能直接等同。初版只支持两端可验证匹配的耳机身份；对不能验证的型号，需明确选择和验证流程，不按名称自动配对。更换本身不连接新耳机，不自动删除旧耳机的系统蓝牙配对。

## 暂停能力依据

- [Android 音频输出变化](https://developer.android.com/media/platform/output)：耳机断开后的暂停需要播放器处理 noisy 事件。
- [Android MediaController](https://developer.android.com/reference/android/media/session/MediaController)：定向控制需要可访问的媒体会话与适用权限。

## 0.4.0 已实现的执行边界

- `HandoffEngine` 消费观察候选，在双方控制就绪、状态新鲜时只创建一个事务；绑定随机事务 ID、目标版本、TLS 会话 epoch、两端观察实例和事件序号。15 秒总预算，结束后 10 秒冷却。期间的新事件不排队补做；暂停/换目标/换实例/重新认证/受保护音频均取消旧事务。
- Mac 通过公开 IOBluetooth 发起一次异步连接，按目标地址匹配唯一 Core Audio 输出设备，最多设置一次默认输出并回读验证。Android 17 通过用户为目标耳机授权的 CDM 关联调用公开 `BluetoothDevice.connect()`，等待目标 profile 和系统媒体预期路由。两端都不预先命令旧端断开。
- 路由验证是系统默认/媒体预期路由，不等于所有播放器的实际输出，也不保证实际有声。独占设备或自行指定输出的播放器需实测。
- 手机指令随已认证 HTTPS 心跳返回（通常 3 秒），不是 WebSocket。收到时扣除完整请求往返与主线程排队时间；过期命令丢弃。硬件操作前持久化消费 ID，进程重启不重放。执行期间最多持有该事务预算的部分唤醒锁，不用于常驻保活。
- 早期版本曾按 Mac 播放器名单筛选；0.4.3 已移除此限制，当前规则见下节。匿名手机播放配置仍存在同用途、同数量替换时漏报的限制。
- Mac 定向暂停仅适配已授权 Music/Spotify，绑定原活动来源与事件；手机可选授权后捕获唯一正在播放的媒体会话，执行时检查 token、状态更新时间、事件和耳机已断开。其他情况跳过。只发 `pause`，不发 toggle，不主动恢复旧端，不回滚连接。
- 暂停最多等待 5 秒且不超过事务总期限；发送 pause 的记录不冒充播放器已确认暂停。即使没有暂停授权，也可验证耳机切换和播放器自身的蓝牙断开暂停。
- 手机超出 10 秒无新鲜状态时，Mac 仍只显示待验证候选，不主动唤醒手机、不依据 120 秒历史盲目抢占。远端通话未知时的无人值守接管仍是待解决项。
- Mac 自动切换开关每次启动默认关闭，适合当前实测阶段；手机授权意图保存并绑定配对身份和目标版本。更换目标后需要重新启用。
- 系统已接受的异步蓝牙连接不能保证在取消瞬间撤回；取消后不继续修改路由或暂停旧端，也不为回滚而断开耳机。

## 0.4.2 首轮实测后的修正

3 秒心跳是兜底，不再是新起播上报节拍：播放/连接/保护状态变化及交接结果立即排队提交，仍串行认证并合并未执行的通知。非媒体提示音不增加手机媒体事件序号，也不覆盖仍在播放的媒体意图。

手机已经调用 connect 后，事务剩余时间只读取目标 profile 和媒体预期路由；媒体配置变化不等同连接失败，也不再发送额外硬件动作。换目标、换实例、撤权、关闭或超时仍结束验证。若路由确认时原起播意图、媒体状态或两端保护状态已变化，只记录路由成功并跳过旧端暂停。Mac 仍在等待修改默认路由的事务保持原来的新意图与保护取消检查。旧端暂停的事件、会话和期限校验不放宽。

首轮 3,080 ms 起播到请求主要受定时心跳链路影响；优化后延迟及蓝牙耗时需重新实测，不承诺零首声外放。


## 0.4.3 通用 Mac 起播检测

按用户要求，接管判断不针对 QQ 音乐或其他播放器特判。Mac 每约 0.2 秒读取 Core Audio 输出活动，新输出进程持续约 0.6 秒才形成候选，不依赖进程名、bundle ID 或播放器名单；浏览器使用同一规则。启动或观察恢复时先建立基线，不将已有播放当作新起播。短输出过滤只是时间阈值，不能准确区分媒体和提示音，较长提示音、静音输出流仍可能触发；持续输出进程内的曲目变化也不等于新边沿。

Android 保持通用播放用途与连接/路由判断。起播后的通用回调和蓝牙建链仍有延迟，不承诺第一帧前完成接管或零外放。

来源识别仅保留于状态展示和可选定向暂停。Mac 的 Music/Spotify pause 适配与起播资格分开；QQ 音乐没有专用暂停指令。无法可靠定向暂停时跳过，保留播放器自行响应蓝牙断开的行为，不发送播放/暂停 toggle。

## 0.4.4 新输出立即判断

用户要求移除 Mac 的 0.6 秒持续输出过滤；上节持续时长规则仅适用于 0.4.3。现在首次观察到新输出就进入既定切换规则，约 0.2 秒采样，不额外等待。原有目标、至少一端连接、状态新鲜度、保护、基线、去重及冷却检查保留。短提示音也可能形成候选；系统输出流活动仍不等同实际可听声音。


## 0.4.5 保护变化后的只读验证

Mac 已提交蓝牙请求后，起播事件、播放状态或任一端保护状态变化不再直接取消验证。事务锁定为只读：不能再次连接、设置默认输出或发送旧端暂停；状态恢复也不会重新放开控制。仍可读取目标蓝牙链路和当前默认输出，记录已由系统完成的接管。未验证路由则按原 15 秒期限结束，不回滚。手机状态过期也转只读。

关闭协调、控制撤权、目标/会话/实例变化和期限耗尽仍结束本轮；只读不等于延长操作授权。请求提交之前仍要求原有起播与保护检查通过。Android 已提交连接后的只读验证规则保持不变。

Android 交接时直接读取现有 profile 代理的当前连接状态，避免使用最长约 1 秒前的观察快照。确认成功后刷新观察摘要再提交结果，避免 Mac 仍读到旧的断开状态。250 ms 验证轮询仅在有界事务中运行；没有新增空闲保活。


## 0.4.6 成功后新起播优先与短时静音

成功（已验证路由）后不再固定冷却 10 秒；失败/未验证超时仍退避 10 秒。交接中已观察到的两端事件记录为已消费，不在结束后补做；路由成功后剩余的尽力暂停也不能阻塞新的反向起播。旧暂停结果不能结束新事务。路由/连接变化重建 Mac 输出边沿基线，Android 媒体路由变化、静音代次变化重新建基线；系统仍报告音乐活动但配置暂不可见时不把缺口当作暂停后再起播。这些过滤无法绝对区分所有播放器内部重配，需实测误抢占。

用户明确授权加入交接期间临时静音。仅在合格事务通过硬件请求前校验后开始，不在空闲、未知目标、两端均断开或失败冷却时静音。成功、失败、取消或 5 秒期限均释放；连接总预算仍为 15 秒，超过静音期限后可能恢复外放，不能为了等待连接无限静音。

Mac：独立预热辅助进程控制内置扬声器 mute 位；不改音量档位，不静音耳机/外接设备，原本静音不接管。启动时恢复遗留记录，写硬件前原子保存；5 秒独立计时，父进程退出/管道 EOF 恢复。辅助进程也被硬杀或系统失效时不能保证立即恢复，下一次启动读取记录恢复。用户已解除静音则不再重写。

Android：普通 APK 无法复用旧 ADB demo 的其他 App 音轨 PlayerProxy/VolumeShaper 控制，改为公开 AudioManager ADJUST_MUTE / ADJUST_UNMUTE，仅针对 STREAM_MUSIC。需要普通 MODIFY_AUDIO_SETTINGS 权限，不增加 ADB/Root/Shizuku。只在媒体预期路由为内置扬声器且原本未静音/非零音量时接管；影响全局媒体声音，不是单播放器增益。不写旧数值音量到新耳机路由。5 秒 Handler + 有限唤醒锁、系统非精确恢复闹钟、持久记录和应用启动恢复；被强制停止会取消闹钟/调度，不能承诺硬杀后严格 5 秒。用户已解除静音则不再写入；普通接口无法区分用户在本来已静音期间再次要求静音的全部意图。

两端提供“恢复声音”按钮，仅释放本 App 持有的保护。播放回调后的静音不能保证零首帧外放。短时静音仍继续播放时间轴，不暂停视频；需测试连接成功恢复、5 秒超时、原本静音和手动调音量。


## 0.4.8 按使用会话失联接管、失败阻止与重连同步

替代 0.4.7 的 300 秒限制。Mac 新起播本地决策，心跳过期与时间流逝都不会单独结束耳机使用会话。手机接管仍需在线认证协调；保留可关闭的“手机暂时离线时允许 Mac 接管”。

1. 建立会话：已认证、目标匹配、采样年龄不足 10 秒的手机目标耳机连接报告，或 Mac 新鲜的本地目标耳机连接确认。只保存在当前 Mac 协调生命周期的内存中。保留最近确认时间用于诊断，不用它倒计时失效。未知状态和连接尝试不构成连接确认。
2. 结束会话：新鲜状态明确两端都断开，或 Mac 重启、睡眠/唤醒、暂停协调、停止功能、更换目标、解除配对。手机报告断开但 Mac 仍连接时会话继续；一端失联不能伪造双端断开。目标不匹配或无效载荷不能授权动作。
3. 失联接管资格：自动切换与失联开关开启、手机此前控制授权有效、Mac 仍参与、目标有效、会话存在且未因失败阻止、Mac 本机耳机明确断开且新起播、无本机保护、最近手机保护状态未阻止。仍只在新事件发起一次连接，不后台周期尝试。
4. 失败处理：失联发起事务连接失败或 5 秒内未验证路由，记录“失联接管已暂停”及失败原因。保留连接历史，不把失败推断为两端断开，也不删掉失败原因。后续新起播不再提交连接或静音，维持现有系统输出；若当前输出为扬声器则外放。普通在线交接的 10 秒失败退避仍保留，不能用它解除失联失败锁定。
5. 重新允许：失败之后的新鲜手机“目标耳机已连接”采样或 Mac 本机连接确认，才能解除失败阻止。按采样时刻判断，并要求手机回传本次失败后下发的恢复标识，排除失败前在途快照；普通心跳、未知状态、失败前的延迟快照、时间流逝和新的播放事件都不能解锁。恢复快照更新状态但不重放起播，因此解除阻止也要等待下一次新起播。
6. 事务：总预算改为 5 秒，临时静音也最多 5 秒；提前成功、失败、取消均立即释放静音。到总期限仍未确认路由则判失败、停止本轮验证并恢复声音，不再继续观察到 15 秒。失败不主动断开耳机回滚，也不强制将用户已选的其他输出改为扬声器。
7. 副作用：失联事务绑定本地协调代次和目标，重连可继续有界只读验证；新的保护或意图变化锁定只读，不再设置路由。失联发起的接管永不补发手机暂停；在线事务原有暂停校验不变。
8. 恢复同步：手机在请求前主线程重新采样连接、媒体预期路由、播放、保护状态，恢复首帧标记 stateSync。Mac 用当前状态更新会话和连接归属，只建立基线，不补做失联期间播放。采样失败不把缓存伪装成当前状态。手机界面显示 Mac 同步的使用会话与失败阻止状态，断联时标为历史状态。
9. 接受的限制：用户接受失联期间入盒、换连其他设备或新通话无法实时获知，可能发起一次不必要连接。连接及路由成功后在目标输出播放；失败恢复原系统输出，并阻止本会话后续盲目尝试。没有时间阈值能证明当前佩戴或通话状态。

| 事件 | 使用会话 / 后续失联接管 |
|---|---|
| 锁屏数小时，只有心跳中断 | 保留，下一次 Mac 新起播可单次接管 |
| 失联接管失败或超时 | 保留历史但阻止新尝试；播放不再反复静音 |
| 新心跳，但无新的连接确认 | 继续阻止 |
| 失败后新的耳机连接确认 | 解除阻止，等待后续新起播 |
| 新鲜状态明确两端断开 | 结束会话，不接管 |
| Mac 退出协调或换目标 | 清空会话与失败状态，重新同步建立基线 |


## 0.4.9 统一 5 秒接管期限

按用户要求，普通双向接管从 Mac 创建事务起共 5 秒，包含连接与路由验证；不是失败后再静音等待 5 秒。Android 对命令 TTL 设置 5000 ms 上限，并扣除往返及主线程排队耗时。成功后的尽力暂停只使用剩余预算，不延长连接事务。旧版本小节的 15 秒仅为历史记录。

超时后释放本 App 静音，不再改路由或补发暂停；失联事务记录失败阻止，在线事务保留失败退避。已交给系统的异步蓝牙请求不保证能撤销，因此操作系统仍可能稍后连上；迟到回调不能把已失败事务改成成功，或继续执行旧端暂停。5 秒是应用期限，调度可能带来少量延迟。


## 0.4.10 手机独立失联接管

目的：Mac 睡眠或网络不通时，手机新起播仍可尝试接回耳机；避免单手机场景每次播放反复连接。已实现，实机验收待进行。

- 最近一次认证响应距今不足 10 秒：沿用 Mac 协调，不另起本地事务。心跳过期只改变决策模式，不触发连接。
- 手机后续新媒体起播：目标及伴生控制授权有效，最近可信同步中自动切换开启，仍有目标耳机的使用会话，本机明确未连接、两端最后已知状态无保护、失败锁未生效、无其他事务，才提交一次连接。已有播放不因断网被重放；本地已连接直接播放。
- 使用会话由新鲜的 Mac 或手机目标连接建立，无固定时间到期。新鲜双断开结束会话。更换配对/目标、明确关闭自动切换、手机用户停止/撤权使本地动作失效。Mac 不可达不等于耳机已入盒，也不证明电脑休眠。
- 连接与媒体路由验证共 5 秒，沿用临时媒体流静音与独立恢复保护。失败/超时恢复声音并锁定后续独立尝试，更多起播、网络重试及时间流逝均不解锁。迟到的系统连接不继续旧事务。
- 失败锁在提交连接前持久化，绑定 Mac 身份与目标版本/地址。手机新鲜本地目标连接，或携带当前恢复标识、重新采样的 Mac 连接确认，才能解除。旧在途响应不能解除失败锁；不会把失败伪造为“两端断开”。
- 成功只记录当前状态，不补发 Mac 暂停；蓝牙断开导致的播放器自动暂停由系统/播放器决定。互不通信且同时新起播仍无法保证全局仲裁，需实测冲突。
- 独立事务开始/结束更新 `localControlGeneration`。恢复通信先同步当前状态；Mac 看到 `localTakeover.active` 时取消重复协调并消费已见事件，代次变化建立观察基线。手机独立执行期间忽略新的远程事务，明确关闭自动切换或撤权仍取消执行。
- 网络连续失败超过约 75 秒或收到 MAC_UNAVAILABLE 后暂停定时 HTTP 轮询，不再由每次起播重启网络重试。有授权且有使用会话、失败锁或事务时继续 `connectedDevice` 前台服务和本地观察；否则结束服务。默认网络恢复、用户连接、系统 BLE/CDM 发现可恢复网络；暂停期间发现入口节流为至少 30 秒，签名及认证成功后恢复常规心跳。
- 进程重建保留失败锁，但不直接复用磁盘上的旧使用会话/自动切换许可；须先得到新的认证同步。无空闲唤醒锁，仍不能保证系统冻结、强行停止或深睡时立即响应。新起播时若系统没有调度 App，独立接管也无法执行。
- 正常退出主动归还仍未实现。Mac 暂停协调/不可用只暂停通信，手机保留已授权会话；手机“暂停连接与自动恢复”或“暂停手机耳机控制”优先停止动作。

验收：在线双向回归；断网超过 10 秒及超过网络重试窗口后的手机新起播；耳机入盒制造 5 秒失败、第二次起播直接外放；失败锁与进程重建；事务中恢复通信不重复请求；用户停止/撤权不自动接管。

## 0.4.11 自动切换偏好持久化

Mac 的自动切换开关保存到 UserDefaults（automaticSwitchingEnabled），应用重新启动时恢复上次选择；未保存过的新安装默认关闭。手机继续使用已有 SharedPreferences.handoff_enabled，开关操作确认写盘后提示成功，更新不清除旧设置。手机开启意愿与当前 ready 分开展示；系统授权、配对身份或目标不匹配不覆盖用户偏好，也不绕过控制校验。解除手机配对仍清除手机控制许可。

暂停保持暂停，恢复通信/应用更新不会把暂停状态强制改为开启。手机自动发现与恢复使用单独的持久化 auto_enabled 开关，保持其原有行为。开关恢复不代表服务保证常驻，也不重放旧播放/事务；启动仍需重新采样并按原规则判断新的起播。
